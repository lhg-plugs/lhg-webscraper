# lhg-scraper-clean：数据清洗与交付

> **合规声明**：清洗环节对全字段再做一次敏感信息扫描（身份证号、手机号、密码、住址等）。命中敏感字段的数据列整体剔除并告警——不该采的数据，洗干净了也不该留；剔除后不在报告里贴原始样本。

目标：把原始采集结果洗成"下游敢直接用"的数据集。清洗的底线：**不创造数据，不美化数据**——脏就是脏，洗不掉就标出来。

## 1. 何时使用

- 采集脚本跑完，拿到原始数据 → 跑全流程
- 下游（分析/入库/展示）抱怨数据脏 → 回到第 3 步看哪类问题漏了
- 只要动了采集字段 → 清洗规则同步更新一遍

## 2. 输入与输出

**输入**：原始数据文件（CSV/JSON/SQLite）、字段说明、去重键定义。

**输出**：清洗后数据集 + 清洗报告（含敏感扫描结论）。报告模板：

```markdown
## 清洗报告：<数据源>（日期）
- 输入 n 行 → 输出 m 行（去重 x 行、丢弃 y 行）
- 归一化：日期 n 处、数字 n 处、枚举映射 n 处
- 空值处理：关键字段丢弃 n 行、非关键字段填默认 n 处
- 敏感扫描：命中 0 / 剔除 × 列（列名清单）
- 交付文件：<路径>（格式、编码 UTF-8、字段说明见附）
```

## 3. 分步方法论

### 第一步：摸底（动手前 5 分钟）

1. 数据量多大？（决定用脚本流式处理还是直接内存处理）
2. 字段有哪些？对照方案卡的数据清单，**多出来的字段先问"哪来的"**——多出来的往往是敏感字段。
3. 去重键是什么？下游要什么格式？
4. 抽 20 行肉眼看一遍：你对数据的第一印象，决定了清洗规则的 80%。

### 第二步：去重

- 按方案卡定义的去重键去重，报告重复率。重复率 >20% 说明采集侧去重没做好，回头修采集。
- 去重保留第一条还是最后一条？提前定：价格类保留最新，内容类保留最早。
- **模糊去重**（标题差几个字算重复）是可选动作，默认不做；要做必须在报告里写清规则。

### 第三步：去噪

常见噪声与处理：

| 噪声 | 处理 |
|---|---|
| HTML 标签残留（`<span>` 等） | 去标签，保留文本 |
| `&nbsp;` / 全角空格 / 首尾空白 | 统一转半角并 strip |
| "加载中…""点击查看更多"占位文本 | 整字段判空 |
| 转义符残留（`\n` 显示成文本） | 还原转义 |
| 重复标点（`！！！`） | 保留语义，不强行"美化"成 `!` |

### 第四步：归一化

- **日期**：统一 ISO 格式（`2026-10-11`）。"3 天前""昨天"这类相对时间按采集时间换算，并在报告注明换算基准。
- **数字**："1.2 万"→12000、"¥29.9"→29.9、千分位去逗号转数值。转失败的标缺失，不猜。
- **枚举**："是/否"→true/false；平台不同的状态词（如"在售/下架" vs "上架/下架"）建映射表，映射表进交付文档。
- **编码**：统一 UTF-8 输出；CSV 加 BOM 方便 Excel 打开。

### 第五步：空值策略（提前定，不许现场发挥）

| 字段类型 | 策略 |
|---|---|
| 关键字段（去重键/主键） | 空值整行丢弃，计数进报告 |
| 数值字段 | 标缺失（null），不许填 0——0 是个有含义的数 |
| 文本字段 | 标空字符串，并在报告注明"n 处空文本" |
| 枚举字段 | 标 `unknown`，不许随机归一类 |

**铁律**：空值不许用编造的值填充。随机生成手机号/姓名去"补全"空值，是造假，不是清洗。

### 第六步：敏感字段二次扫描（硬性）

```
python3 <插件目录>/scripts/audit/webscraper_audit.py --scan-fields <清洗后文件>
```

- 命中 → 该列整体剔除，报告写"因合规原因剔除 × 列（列名）"。
- 报告里不贴原始样本——样本本身也是敏感数据。
- 剔除后下游字段对不上？那是方案阶段字段定错了，回去改方案，不许"先留着"。

### 第七步：交付

- 文件命名：`<数据源>_<日期>_clean.<格式>`，与原始文件区分。
- 附字段说明：字段名 / 类型 / 含义 / 示例 / 空值含义。
- 附采集报告引用：让下游知道数据怎么来的、限流是否生效。

## 4. 反模式

- ❌ 用编造的值填空值——这是造假，不是清洗
- ❌ "这个字段看着像手机号，但先留着吧"——看着像就按敏感处理
- ❌ 去噪时"顺手"改写原文案——清洗不改写，只整理格式
- ❌ 相对时间不换算直接存"3 天前"——三天后这条数据就错了
- ❌ 清洗报告只写"已清洗"三个字——没有过程的结论不可信

## 5. 自检与反馈

**质检门**（交付前逐项打勾）：

- [ ] 去重率、丢弃数、归一化数与报告一致（抽 50 行复核）
- [ ] `--scan-fields` 跑过，无敏感列残留
- [ ] 空值策略按第五步表格执行，无编造填充（抽查 20 个空值）
- [ ] 日期/数字归一化抽查 20 处，转失败的已标缺失
- [ ] 交付文件名、字段说明、采集报告引用齐全

**标准冒烟用例**：用一份含重复行、HTML 残留、"3 天前"日期、空值的 200 行样本走全流程 → 输出行数 = 输入 − 去重 − 丢弃，报告数字对得上；再混入一个"手机号"列 → 第六步必须剔除并告警。

**一键提 issue**：发现流程缺口或误判，以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-webscraper/issues，正文写清"复现步骤 → 实际表现 → 期望表现"。

## 6. 清洗脚本骨架（伪代码，按需翻译成你的语言）

```
读原始文件 -> rows
seen = 空集合; out = []
for row in rows:
    if 去重键(row) in seen: 重复计数++; continue
    seen.add(去重键(row))
    row = 去HTML残留(row); row = 统一空白(row)
    row = 归一化日期(row); row = 归一化数字(row)
    if 关键字段为空(row): 丢弃计数++; continue
    out.append(row)
跑敏感列扫描(out的列名) -> 命中则剔除整列并告警
写清洗文件 + 写清洗报告(输入/输出/去重/丢弃/归一化数)
```

骨架里的每一步都对应第 3 节的一个小节，加新规则时先更新小节，再改骨架——文档与代码同构，改一处不改另一处就是未来的坑。

### 交付文件命名与版本

- 命名：`<数据源>_<日期>_clean.<格式>`，如 `tech_news_20261011_clean.jsonl`。
- 原始文件保留 30 天再归档，清洗文件永久保留；两者放同一目录，方便追溯。
- 同一数据源第二次清洗 → 文件名日期区分，不覆盖旧文件，清洗报告注明"第 N 次清洗"。
