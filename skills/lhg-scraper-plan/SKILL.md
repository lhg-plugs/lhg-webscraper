# lhg-scraper-plan：采集方案设计

> **合规声明**：本 skill 只设计**公开可访问数据**的采集方案；遵守目标站 robots.txt 与服务条款；不设计任何绕过登录、付费墙、验证码的环节；采集频率默认限流。方案评审时任一环节触碰红线即整体否决。

目标：动手写代码之前，先把"采什么、怎么采、采多快、怎么停"想清楚，输出一张**采集方案卡**。没有方案卡的采集任务不许开工。

## 1. 何时使用

- 新开一个采集任务 → 跑全流程，输出方案卡
- 已有脚本要换目标站 → 只跑第 2、3 步（站点分析 + 请求策略），确认差异点
- 采集效果不好（缺字段、被限流）→ 回到第 2 步重新做站点分析，别急着加并发

## 2. 输入与输出

**输入**：目标站点 URL、采集需求（一句话中文，如"每天抓取某科技媒体的头条标题和发布时间"）、是否增量、页面是否需要 JS 渲染。

**输出**：采集方案卡（Markdown 表格）+ 风险清单。方案卡模板：

| 项 | 内容 |
|---|---|
| 目标站点 | URL + 站点类型（静态 HTML / JS 渲染 / 开放 API） |
| 合规结论 | robots.txt 预检结果 + ToS 结论（通过/拒绝） |
| 数据清单 | 字段名 × 类型 × 是否必需 × 示例值 |
| 请求策略 | 请求方式、UA、限流间隔、并发上限、超时、重试 |
| 解析策略 | 解析器选型、字段定位方式、翻页方式 |
| 增量策略 | 去重键、断点续传、水位线字段 |
| 交付物 | CSV / JSON / SQLite + 字段说明文档 |

## 3. 分步方法论

### 第一步：站点分析（15 分钟，不许跳过）

1. **看页面类型**：右键"查看网页源代码"，目标数据在源码里 → 静态站；不在 → JS 渲染站（考虑无头浏览器或找页面调的 API）。
2. **找数据源头**：渲染站优先找页面请求的 JSON API（浏览器开发者工具 → 网络面板），API 返回结构化数据，比解析 HTML 稳一个数量级。
3. **看翻页机制**：页码参数（`?page=2`）、游标（`cursor=xxx`）、滚动加载（需渲染）。游标翻页最稳，滚动加载最脆。
4. **看反爬信号**：首次访问是否弹验证、headers 里有没有风控字段、连续请求几次后是否变慢。**只做观察，不做对抗测试**——高频试探本身就是攻击行为。
5. **做合规预检**：读 `/robots.txt`（用 `/lhg-webscraper:check-robots`），看 ToS 有没有"禁止自动化采集"条款。任一红灯 → 任务终止，输出拒绝说明。

### 第二步：数据清单（先定字段，再写代码）

- 字段按"必需 / 有更好 / 不要"三档划分。**"不要"档默认包含**：身份证号、手机号、密码、住址、银行卡等个人敏感信息——这些字段连"先采了再说"都不许。
- 每个字段写一个示例值。写不出示例值 = 你还没看懂页面，回去看。
- 字段名用英文小写下划线，清洗环节直接沿用，避免中英混杂。

### 第三步：请求策略（礼貌优先）

| 参数 | 默认值 | 说明 |
|---|---|---|
| 请求间隔 | ≥1 秒 | robots 有 Crawl-delay 按更大的来 |
| 并发 | ≤3 | 默认串行，需要再加 |
| 超时 | 15 秒 | 所有请求显式设置 |
| 重试 | 指数退避，最多 3 次 | 只对 429/5xx/网络异常重试，4xx 不重试 |
| UA | 如实标识 | 格式：`用途/版本 (联系方式)`，如 `price-monitor/1.0 (contact@example.com)` |

选型建议：静态站用 requests/httpx；渲染站用无头浏览器；有开放 API 直接调 API。**不许为了"快"选激进并发**。

### 第四步：解析策略（稳字当头）

1. **定位符优先级**：稳定属性（`data-*`、id）> 语义标签（article/h2）> CSS 类名 > XPath 绝对路径。类名最容易变，绝对路径一变全挂。
2. **防御性解析**：每个字段解析失败不抛异常，记缺失继续；整页结构变化（关键容器找不到）则停机告警，而不是产出半残数据。
3. **翻页**：页码/游标参数化；滚动加载用"滚动→等待新内容→比对数量"循环，加最大滚动次数兜底。
4. **编码**：统一按 UTF-8 处理，遇到乱码先查响应头 charset，别猜。

### 第五步：增量策略（采集不是一次性买卖）

- **去重键**：每条数据一个稳定唯一键（文章 URL、商品 ID）。入库前查键，存在则跳过。
- **水位线**：用发布时间/自增 ID 做水位线，下次只取大于水位线的数据。
- **断点续传**：进度（页码/游标/水位线）落盘，任务中断后从断点继续，不是从头再来。
- **全量 vs 增量**：首次全量建基线，之后增量。没有"每次都全量"的设计——那是对目标站和自己的双重浪费。

### 第六步：交付物定义

- 小数据（<10 万行）：CSV（UTF-8 with BOM，方便 Excel 打开）或 JSON Lines。
- 结构化查询需求：SQLite 单文件，开箱即用。
- 必须附：字段说明（字段名/类型/含义/示例）、采集报告（请求数/成功率/耗时/平均间隔，证明限流生效）。

## 4. 反模式

- ❌ 不看 robots.txt 直接开爬——合规预检是第零步，不是可选项
- ❌ "先采了再说，字段以后再定"——字段不定，解析写两遍
- ❌ 用绝对 XPath 定位——页面改一次版，脚本全挂
- ❌ 每次全量重采——浪费目标站带宽，也浪费自己的时间
- ❌ 4xx 也重试——404 重试 3 次除了多 3 次请求，什么都得不到
- ❌ 采集"顺手"多拿几个敏感字段——红线，没有"顺手"

## 5. 自检与反馈

**质检门**（方案卡发布前逐项打勾）：

- [ ] 合规结论是"通过"，robots.txt 预检命令跑过且有记录
- [ ] 数据清单无敏感字段（用审计脚本 `--scan-fields` 扫一遍字段名）
- [ ] 请求间隔 ≥1 秒、并发 ≤3（或有 robots Crawl-delay 依据的更大值）
- [ ] 每个字段有示例值，解析定位符不是绝对 XPath
- [ ] 去重键与水位线字段已定义，断点续传有落盘位置
- [ ] 交付格式与字段说明模板已定

**标准冒烟用例**：拿本仓库 `fixtures/good` 的目标站描述走一遍本流程，6 步应全部产出文档，无红线拦截；再拿一个"需要登录才能看"的假想站点走一遍，第一步合规预检必须输出拒绝。

**一键提 issue**：发现流程缺口或误判，以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-webscraper/issues，正文写清"复现步骤 → 实际表现 → 期望表现"。

## 6. 方案卡填写示例（照着填）

假设需求："每天采集某科技媒体公开头条的标题与发布时间"。

| 项 | 内容 |
|---|---|
| 目标站点 | https://example-tech.com，静态 HTML 站 |
| 合规结论 | ✅ 通过：robots.txt 允许 `/news` 路径，Crawl-delay 无，ToS 未禁止自动化采集（2026-10-11 检查） |
| 数据清单 | title（文本，必需，示例"AI 芯片出货量翻倍"）、publish_time（日期，必需，示例 2026-10-10）、author（文本，有更好） |
| 请求策略 | requests；UA `tech-digest/1.0 (contact@example.com)`；间隔 2 秒；串行；超时 15 秒；429/5xx 指数退避重试 3 次 |
| 解析策略 | CSS 选择器 `article h2` 定位标题（备用 `data-role="title"`）；翻页 `?page=N` 参数化 |
| 增量策略 | 去重键=文章 URL；水位线=publish_time；进度落盘 `state.json` |
| 交付物 | JSON Lines + 字段说明；采集报告附请求数/成功率/平均间隔 |

**风险清单**：

- 页面改版导致选择器失效 → 防御性解析 + 停机告警
- 站点新增 Crawl-delay → 请求间隔按新值调整
- ToS 更新 → 每季度复查一次 ToS（写进日历提醒）

### 方案评审三问（方案卡定稿前）

1. 如果目标站明天改版，脚本哪部分先挂？（答不上来 = 解析策略太脆）
2. 如果数据量翻 10 倍，限流参数还成立吗？（不成立 = 现在就要定分级策略）
3. 如果站点发邮件说"请停止采集"，我们几分钟能停？（答不上来 = 缺停机开关）

### 常见站点类型速查

| 类型 | 识别信号 | 首选策略 |
|---|---|---|
| 静态 HTML | 源码里有目标数据 | requests + CSS 选择器 |
| 服务端渲染+API | 网络面板有 JSON 接口 | 直接调公开 API |
| 纯前端渲染 | 源码无数据，需 JS | 无头浏览器正常加载 |
| 反爬严格站 | 首访就弹验证 | 先做合规评估，大概率停手 |
