# lhg-scraper-compliance：采集合规红线

> **合规声明（置顶，不可绕过）**：本插件只采集**公开可访问**的数据；遵守目标站点的 robots.txt 与服务条款（ToS）；**不**绕过登录、付费墙、验证码（CAPTCHA）；采集频率限流，不给目标站造成负担；使用者自行承担法律责任。任一环节触碰红线，插件必须**直接拒绝并说明原因**，不提供任何变通方案。

目标：把"能不能采"变成一道开卷必答题。答完五问，有一题答错就停手——合规没有"差不多"。

## 1. 何时使用

- 任何采集任务动手前 → 先跑第 2 节五问 + 第 3 节预检
- 用户说"这个站要登录/要会员/有验证码，想办法" → 直接跳到第 6 节拒绝话术
- 采集代码写完后 → 跑第 5 节审计清单
- 不确定某个字段能不能采 → 查第 4 节敏感字段判定表

## 2. 输入与输出

**输入**：目标站点 URL、目标路径、拟采集字段清单。

**输出**：合规结论（二选一，不许有第三种）：

- ✅ **通过**：附 robots.txt 预检记录 + ToS 检查记录 + 字段清单（无敏感字段）
- ❌ **拒绝**：写清触碰的是哪条红线 + 拒绝话术（第 6 节）+ 可行的合法替代建议（如"用官方 API""联系站点要授权"）

## 3. 分步方法论

### 第一步：五问拒绝清单（任一"是"即拒绝）

| # | 问题 | 是→ |
|---|---|---|
| 1 | 数据是否需要登录后才能看到？ | 拒绝：绕过登录不在本插件能力范围 |
| 2 | 是否涉及付费墙 / 会员专区内容？ | 拒绝：付费内容请走正规订阅 |
| 3 | 是否需要绕过验证码 / 人机验证？ | 拒绝：验证码就是"请勿打扰"的牌子 |
| 4 | 目标站 ToS 是否明确禁止自动化采集？ | 拒绝：ToS 是站点定的规矩 |
| 5 | 采集字段是否含个人敏感信息？ | 拒绝（或删字段后重审）：见第 4 节 |

**注意**：第 1–3 问的"变通"（借用他人账号、用打码平台、模拟登录）同样拒绝——换了个姿势绕过，还是绕过。

### 第二步：robots.txt 预检

1. 拉取 `https://<域名>/robots.txt`（用 `/lhg-webscraper:check-robots` 或审计脚本 `--check-robots`）。
2. 按 RFC 9309 语义判定：找最匹配的 User-agent 组，最长匹配定 Allow/Disallow。
3. 看 Crawl-delay：有则遵守，无则按默认（间隔 ≥1 秒）。
4. 有 Sitemap：优先从 sitemap 拿 URL 清单，减少对站点的无效请求——这是"礼貌采集"的加分项。
5. 拉取失败（404/超时）：视为"无明确禁止"，但仍按保守策略执行，并在报告注明"未取到 robots.txt"。

**关键认知**：robots.txt 是"君子协定"，不是法律；但无视它，等于告诉全世界"我不讲规矩"。合规采集把它当硬门。

### 第三步：ToS 检查

1. 找到目标站的服务条款 / 使用协议页面（通常在页脚）。
2. 搜索关键词：爬虫、scraping、自动化、bot、crawler、数据采集。
3. 明确禁止 → 拒绝；没提 → 结合 robots.txt 与采集强度综合判断，并在报告里写清"ToS 未明确禁止，已按保守策略执行"。

### 第四步：敏感字段判定表

| 字段类型 | 示例 | 结论 |
|---|---|---|
| 身份标识 | 身份证号、护照号、社保号 | ❌ 不采 |
| 联系方式 | 手机号、个人邮箱、住址 | ❌ 不采 |
| 账户秘密 | 密码、支付密码、银行卡号 | ❌ 不采 |
| 公开业务数据 | 商品价格、文章标题、发布时间 | ✅ 可采 |
| 聚合统计 | 销量总数、评分均值 | ✅ 可采（不含明细里的个人信息） |

**灰区处理**：拿不准的字段（如"用户昵称+评论内容"），默认按"不采"处理；确需采集时做脱敏（哈希 ID、截断）并在报告中说明依据。

### 第五步：代码审计清单（写完代码后）

跑审计脚本 `--target`，重点看四类：

- **blocker 必清零**：无 robots 检查（WS-CMP-001）、绕过意图（WS-CMP-002）、敏感字段（WS-SEC-001）、硬编码凭证（WS-SEC-002）
- **warning 修或豁免**：无限流（WS-RAT-001）、无 UA（WS-UA-001）、无超时（WS-NET-001）、硬编码 Cookie（WS-HON-001）
- **发现绕过类代码**：要求删除，不接受"加注释说明"作为修复
- 审计脚本本身不联网"试爬验证"——合规结论来自文本（robots/ToS），不是"试一下"

## 4. 反模式

- ❌ "robots.txt 只是建议，不理它"——技术上能爬 ≠ 可以爬
- ❌ "先采了再说，被发现再停"——这是故意的，不是疏忽
- ❌ "换个 UA / 换 IP 继续"——被站点限流后换身份绕过，属于对抗行为，拒绝
- ❌ "只采一点点应该没事"——量小不改变性质，该拒绝还是拒绝
- ❌ "用户说他有授权"——口头授权不算数，要站点方的书面/页面公示授权
- ❌ 把登录态 Cookie 写进脚本"借用一下"——过期、泄露、违反 ToS，三宗罪

## 5. 自检与反馈

**质检门**（合规结论发布前逐项打勾）：

- [ ] 五问清单逐项有书面答案，无跳过
- [ ] robots.txt 预检命令跑过，结论记录在案（含 Crawl-delay）
- [ ] ToS 检查过，关键词搜索无"禁止自动化采集"（或已拒绝）
- [ ] 字段清单跑过 `--scan-fields`，无敏感列
- [ ] 代码审计 blocker 清零；绕过类代码已删除（不是注释掉）

**标准冒烟用例**：用"公开新闻列表页"走一遍 → 结论必须是通过；用"需登录的个人中心页"走一遍 → 第一步第 1 问必须触发拒绝；用"带验证码的票务页"走一遍 → 第 3 问必须触发拒绝。

**一键提 issue**：发现流程缺口或误判，以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-webscraper/issues，正文写清"复现步骤 → 实际表现 → 期望表现"。

## 6. 判定实例（三个真实形态的案例）

### 案例 A：公开的政府招投标公示页 → 通过

- 五问：全否。robots.txt 允许，ToS 无禁止条款，字段只有项目名称/金额/日期。
- 结论：✅ 通过。按默认限流执行，交付 CSV。

### 案例 B：某论坛"登录后可见"的帖子详情 → 拒绝

- 五问第 1 问：是（需登录）。用户说"用我的账号 Cookie 就行"。
- 结论：❌ 拒绝。话术："目标数据需要登录后可见，属于第 1 条红线。借用个人登录态会把账号暴露给脚本，且通常违反站点 ToS。建议联系论坛方申请数据合作。"

### 案例 C：电商平台的公开商品列表（含"用户手机号"字段）→ 删字段后通过

- 五问前 4 问否，第 5 问：是（字段含手机号）。
- 结论：⚠️ 删字段后重审。去掉"手机号"列，剩余商品名/价格/销量重新走五问 → ✅ 通过。

## 7. 标准拒绝话术（直接用，不许改得委婉到失去立场）

> 这个需求我接不了，原因是：<触碰的红线，如"目标数据需要登录后可见，属于第 1 条红线">。
>
> 本插件只采集公开可访问的数据，不绕过登录、付费墙、验证码。如果你确实需要这些数据，建议走合法渠道：联系目标站点申请官方 API 或数据授权。
>
> 如果你手里有站点的书面授权，把授权依据发我，我重新做合规评估。

### ToS 关键词速查（中英对照）

中文站搜：爬虫、采集、抓取、自动化、机器人、bot、数据挖掘。
英文站搜：scraping、crawling、automated access、bot、data mining、harvest。

搜到"禁止"类表述 → 拒绝；搜到"需授权/联系我们" → 按联系方式申请授权后再评估；什么都没搜到 → 在报告写"ToS 未明确提及自动化采集"，仍按保守策略执行。

### 授权证据清单（用户声称"有授权"时要这四样）

1. 授权方：站点官方（不是"朋友说的"）
2. 授权范围：哪些路径/字段（截图或链接）
3. 授权形式：页面公示或书面文件（口头不算）
4. 有效期：过期了重新评估

四样缺一样 → 按无授权处理，先拒绝。
